# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

No version has been tagged or published as a release yet. Until they are, a version's code is the commit that sets `VERSION` in `fanctl.py` to it, and the dates are those commits' dates.

## [1.4.0] - 2026-10-26

### Added

- **A warning when a target is a guess.** For a sensor where neither `setPointTemperature` nor `targetTemperature` is usable (missing, below 1 °C, or at or above the alert limit), fanctl uses 0.65 × its alert limit, a ratio measured only on the reference switch, and nothing said so except the `(source)` column in `--probe`. Now the daemon logs `N sensor(s) report no usable EOS setpoint (none, or not between 1 C and the alert limit), so their target is 0.65 x alert limit, a ratio measured on a DCS-7050TX-64-R: …` at the first poll and daily after, and `--probe` prints it as a `WARNING:` before its verdict. The reference switch reports a setpoint for every sensor, so it never shows there. A new off-box test covers it.
- **The guard has a version.** `fanctl-guard.sh` carries fanctl's version number, logs `fanctl-guard <version> started: first check in 180 s, then every 60 s` when it starts (it used to log nothing), and logs `fanctl X is running with fanctl-guard Y; install both files from the same release` once if the live fanctl is from another release. Mixed versions could only be told apart by comparing hashes by hand. Because of the version line, the guard file now changes with every release. New end-to-end tests cover both lines, and a test pins the number to fanctl's.
- **The tests check `SHA256SUMS` and the test count.** `SHA256SUMS` was updated by hand, and nothing noticed when it fell behind `fanctl.py` or `fanctl-guard.sh`, so the documented install check would have failed on every switch. A new off-box test recomputes both hashes. README, OPERATIONS.md and SECURITY.md now say that it shows a copy is intact, not where it came from. The suite's size, stated in both README and VALIDATION.md, is now given only in VALIDATION.md, and another test checks it.
- **Tests for the benchmark and the step-test analysis.** `bench/bench.py`, `sweep.py`, `steady_inlets.py` and the analysis scripts in `measurements/` were checked only by rerunning them by hand, although every recorded result passes through them. `tests/test_research.py` now runs them on the tracked data and checks that they reproduce what is recorded: `measured_model.json` to within float rounding, `bench/results/model_validation.txt`, the step-test numbers in docs/VALIDATION.md, rows of `canonical.json`, `steady_inlets.txt` and `sweep_wmin.json`, and the summary lines of every recorded sweep. Their long functions are split into small ones, with the same output. The analysis tests need NumPy and are skipped without it; CI installs it for the Python 3.10 and 3.12 jobs. Only the candidate controllers in `bench/variants/` stay untested, as recorded. The tests found that `bench.run_one()` left the last candidate in place of fanctl's own controller for the rest of the process; it now puts fanctl's back.
- **A glossary.** docs/DESIGN.md now defines excess, weight, binding sensor, band, probe, back-off, hand-off, hold, resume and the other terms, with the names the code, the log and the status file use for them. "Hold" now means only time under EOS control: the band tables and the module docstring say "no change" for the speed fanctl leaves alone in the band, and `--probe` says `it would keep the fans at …`. The module docstring and `--up-interval`'s comment describe the at-target raise as it is.
- **CI and CONTRIBUTING.md.** `.github/workflows/test.yml` runs the suite on Python 3.9 with bash 4.2, the switch's versions, as an ordinary user and as root, in the image `tests/eosenv/Dockerfile` builds (it checks the bash 4.2 source against a SHA-256 taken from a copy whose GNU signature verified), and on Python 3.10 and 3.12. It also checks `sha256sum -c SHA256SUMS` and runs shellcheck on `fanctl-guard.sh`. CONTRIBUTING.md says how to run the tests and what the two on-box files must stay compatible with. The end-to-end tests no longer `chmod` the tracked `tests/fake_fastcli.py`, so the suite runs from a read-only checkout or one owned by another user. Two end-to-end tests that failed now and then on a loaded machine wait for what they check: one stopped fanctl before it had logged its hand-off, and one while it was still starting up.

### Changed

- **fanctl doesn't take over while EOS runs the fans above its ceiling.** It used to wait only if its own last hand-off had been "not enough even at the ceiling". At startup, or after any other hand-off, it took over from an EOS running the fans at, say, 95 % and cut them to the 70 % ceiling in one step, although EOS may have been cooling something fanctl doesn't read (optics, a skipped or ignored sensor). Now it waits under EOS control (`EOS runs the fans at N%, above fanctl's 70% ceiling`), and `--probe` says so, instead of claiming it would take over at the ceiling as "the speed EOS is running now". On the reference switch EOS runs about 60 %, so nothing changes there. The memory file no longer carries `ceiling_release`. A new off-box test covers it.
- **The memory file is written at every poll.** It was written only on some events (a change, and every poll while EOS had control), chosen by a hand-kept list. After hours at one speed it was older than `hold_max` (4 h), so a SIGKILL restart (EOS's daemon `shutdown`) that found the fans in auto (the guard's restore) ignored it and took over at EOS's 60 %, then spent an hour creeping back down. Now it is rewritten at every poll, like the heartbeat (both are in RAM, `/run/fanctl`), and such a restart resumes at the old speed if nothing has got hotter. A probe back-off halved on a poll without a change is no longer lost either. While fanctl is paused it doesn't record the operator's speed as its own. The file no longer carries `mode` and `speed`, which nothing read. A new off-box test covers it.
- **fanctl warns when `--state-file` or `--lock-file` moves a file the guard watches.** The guard watches `/run/fanctl` (unless its `FANCTL_LOCK` and `FANCTL_STATE` say otherwise), so moving the heartbeat or lock under the daemon made it restore automatic control every minute while fanctl paused, and the log said only `fan setting changed outside fanctl`. Now fanctl logs `WARNING --lock-file … and --state-file …: fanctl-guard.sh watches /run/fanctl/fanctl.lock and /run/fanctl/fanctl.status.json unless its FANCTL_LOCK and FANCTL_STATE name others; …` at startup (not in a dry run, which the guard never trusts anyway), and `--help` and DESIGN.md say the options are for tests and runs by hand. It warns instead of refusing because the tests and runs by hand without root need them. A new end-to-end test covers it.
- **`tools/monitor.py` and the step test share one SSH session.** `measurements/fan_step_test.py` kept a copy of the monitor's SSH shell, and the copies had drifted. Both now use `tools/eos.py`, which reads the login from the environment once at start-up: a missing `SWITCH_HOST` or `SWITCH_USERNAME` prints the usage instead of a `KeyError` (the monitor used to retry that every 30 s), an `enable` that doesn't reach the `#` prompt is an error in both, and the step test's session refuses any command but `show`, an override in its 30–70 % range and the two hand-back lines. The monitor's poll records now carry each PSU's input current, as the step test's do. New off-box tests run both against a fake switch.
- **The benchmark's scripts run from anywhere and share one sweep.** `bench/seeds.py`, `sweep_cfg.py` and `sweep_wmin.py` each kept a copy of the 20-seed safety sweep and its summary, opened the plant model relative to the current directory, and wrote `seeds.json` into it or overwrote the tracked `results/sweep_wmin.json`. They are replaced by `bench/sweep.py CANDIDATES [--json OUT]`, where a candidate is a variant, fanctl setting overrides and environment variables; it prints both old formats and writes only the file named. `bench.py` takes `--cfg`, `--seed` and `--model` instead of the `BENCH_CFG` and `BENCH_SEED` environment variables, and its minutes over target count the configured poll interval instead of a fixed 15 s. The plant model is kept once, in `measurements/measured_model.json` (`bench/measured_model.json` was a byte-for-byte copy). On the same fanctl, every rerun sweep gives the same numbers as before.
- **One step-test model builder.** `measurements/analyze.py --model` wrote a second kind of plant model (no measured curve, no time-constant scaling) that the benchmark would have read with a silent fallback to the power-law fit, and its fitting code was a copy of `build_model.py`'s. `--model` is gone; `build_model.py` now builds the model from `analyze.py`'s steady states, power-law fit and time constants, and gives the same model as before. `analyze.py` no longer ignores a missing or broken sensor-description file.
- **Python 3.9 or newer.** The README and OPERATIONS.md said 3.6 or newer, which was never tested. fanctl is tested on 3.9 (the switch has 3.9.17), 3.10 and 3.12; older versions are untested.
- **The docs say what has run on hardware, and how to report privately without GitHub's reporting switched on.** README and VALIDATION.md now say that every run on the reference switch used 1.3.0 or 1.3.1, and that what 1.3.2 and this release changed is tested only off-box. SECURITY.md sent reporters only to GitHub's private vulnerability reporting, which is off unless the repository turns it on; it now also says to ask for a private contact in an issue that gives no details. Site-specific details the validation notes didn't need (the switch's uptime, what its links connect to, the monitoring host) are gone.
- **A setpoint must be a plausible temperature.** 1.3.2 and earlier took any `setPointTemperature` or `targetTemperature` above 0 and below the alert limit as EOS's target, so a setpoint of 0.5 °C was controlled against. Now a setpoint must be 1–150 °C, as a reading and an alert limit must; one below 1 °C gives the 0.65 × alert limit target and the warning above. The reference switch's setpoints are 35.75–80 °C, so nothing changes there. An off-box test covers it.

### Fixed

- **`--probe` says what fanctl really does.** Its verdict kept its own copy of the band rules, which 1.3.2 had left behind: at target it said the fans would `go UP 5% now and again every poll`, inside the raise zone it said `a minute` whatever `--up-interval` was, and at the floor it still said `come DOWN`. Now the probe runs fanctl's own controller, poll by poll, on the readings it took, and prints the log lines of the next changes the daemon would make if the readings stayed as they are, for example `after 300 s: lowering fans -> override 38%: binding: …`, or `it would keep the fans at override 30% (no change within 3600 s)`. It looks twice the longest wait ahead, but at most 2000 polls, so with waits of a day it answers in under a second off-box instead of after a minute, and it says how far it looked (`(no other change within N s)` after a single change). The module docstring's raise rule is corrected the same way. Seven new off-box tests cover it.
- **Every option has a range.** `--flap-window`, `--reconcile` and `--summary` accepted any number, and `--hold-max` had no upper bound: `--reconcile 0` read running-config at every poll, and a negative `--summary` logged a status summary at every poll as `… in the last -1 min`. Each range was a hand-written check, so a new option could go without one. Now every option's default and range sit in one table, so none can be added without a range: `flap_window` is 0–86400 s, `reconcile` and `summary` 60–86400 s and `hold_max` 1–86400 s, and `--help` shows each option's range. A value outside it gives `invalid settings, not starting: <option> must be <low>..<high> <unit>`. `--release-excess 0` (hand the fans to EOS at any reading over target) is now accepted; it used to need more than 0. A new off-box test tries a huge and a hugely negative value for every option.
- **The status after a rejected override shows the hand-off.** When EOS rejected an override, fanctl handed the fans back to EOS in the same poll, but the status file (and `--status`) for that poll still showed the decision it had abandoned, for example `event: resume` with the reason for taking over, next to `fanctl wants auto`. Now that poll reports `event: release` with `could not apply override N%: …` and the hold it started. The hand-off write now takes the same path as every other one: it isn't sent when EOS already has the fans, and if it fails it logs `could not set automatic fan control … (retrying every poll)` rather than `could NOT restore automatic fan control`, which now only comes from a stopping fanctl. A new off-box test covers it.
- **A fault right after taking over records the right inlet.** When fanctl took over again after a fault hand-off and another fault came at the very next poll, it saved the speed it had just chosen together with the inlet from before the earlier hand-off, which could be hours old. The next "nothing got hotter" check before resuming at that speed then compared against the old inlet. Now the speed, hottest excess and inlet are always recorded together. A new off-box test covers it.
- **PSU fans are checked as strictly as fan-tray fans.** The cooling JSON's PSU fan section was skipped without a word when it was missing, not a list, or a slot had no fans, and PSU fans didn't count toward the "fan disappeared" check, so an EOS release that reshaped that section, or a PSU fan entry that vanished, removed every PSU-fan check while fanctl kept the fans low. Now an odd shape is a fault (`unexpected powerSupplySlots fan data`, `unexpected PSU fan entry`, `PowerSupplyN reports no fans`), and PSU fans count toward the fan count, so one vanishing gives `fan count dropped from 6 to 5`. A PSU left out with `--ignore-psu` is still skipped, and a cooling JSON with no PSU section at all (from the first poll) is still accepted, as in the temperature JSON. `--probe` now counts every fan it checks (`fans (fan trays and PSUs): 6`). Two new off-box tests cover it.
- **A damaged memory file can't stop fanctl starting.** Some fields of `/run/fanctl/fanctl.memory.json` were checked and others passed straight to `int()`/`float()`. A non-finite number (`Infinity`, which Python's JSON reader accepts) in `hot_hold` or `fault_hold` made every start fail with `internal error`, a ProcMgr restart loop until the file aged past 4 h, and in `hold_left` it gave a hold that never ended. Now every field is checked when the file is read; a bad one, including an integer too large for any float, makes fanctl log `ignoring unreadable … : <field> is …` and start as if there were no memory, and a restored hold is never longer than `hold_max`. Unreadable JSON is logged too instead of skipped silently. Such an integer in EOS's JSON is now a fault of that one field (for example `inlet (ambient) temperature … is not plausible`) instead of `error while judging switch environment` for the whole poll. New off-box tests cover eleven kinds of damage and the oversized number from EOS.
- **Only one fanctl runs, even if the lock file is removed.** If `/run/fanctl/fanctl.lock` was removed while a second fanctl waited for it, the running fanctl locked a new file and let go of the old one, and the waiting fanctl then started on the deleted file: two fanctls set the fans and overwrote each other's heartbeat and memory. A fanctl that found the new file held by another process logged `… was replaced and is held by another process` and went on controlling. Now a fanctl that gets the lock checks that the file it locked is still the one at the path, and waits again if not; a running fanctl whose lock file another process now holds logs `… was replaced and is held by another process; stopping, and leaving the fans, heartbeat and memory to it` and exits (status 1) without touching the fans. Two new end-to-end tests cover it.
- **The at-target raise really waits for the fans after a 1 °C step.** 1.3.2 meant to raise again within `up_interval` (60 s) only while it was still getting hotter, but it judged that partly from each sensor's 4-poll mean, which keeps rising for three polls after a whole-degree sensor steps onto its target. So when a PHY sensor reached its target by a 1 °C step and stayed there, the fans still went up 5 % at every 15 s poll (+20 % in 45 s), as in 1.3.1. Now a later raise comes at once only if the hottest raw excess (reading minus target) is higher than at the last raise, or a reading at or over its target rose more than 1 °C over the last 4 polls, which whole-degree rounding can't explain (a load still building). After a 1 °C step onto the target the fans now get one raise and then `up_interval`. In the controller benchmark, overshoot, fan speed and warm-spell results are unchanged, changes per day are slightly lower (all plants 23.9 against 24.4), and load steps went over target in 4 of 20 seeds against 3 (`bench/results/v1.3.2.txt`). Two new off-box tests cover it.
- **A lagging cooling status isn't taken for someone else's change.** When the cooling status disagrees with fanctl's setting and running-config can't be read, fanctl writes nothing that poll and believes the status at the second such poll. A poll in between where running-config did confirm fanctl's setting (the status merely lagging) didn't start the count over, so after fanctl stepped from 40 % to 38 % under a status still showing 40 %, two failed running-config reads with a good one between them made it log `fan setting changed outside fanctl (override 38% -> override 40%)` and pause, with the fans at 38 % and nobody having changed anything. Now a confirmation clears the doubt. A new off-box test covers it.
- **A failed hand-off while paused is retried.** When fanctl was paused on an operator's low override (below the ceiling) and something became hot or faulty, it wrote `auto` once. If that write failed, for example a FastCli timeout while the switch was under stress, fanctl logged `could not set automatic fan control ... (retrying every poll)` but never wrote again, so the fans stayed at the low override for as long as fanctl ran. Now it retries at every poll until EOS has the fans, as it does when it isn't paused, and meanwhile the paused alarm ends `fanctl is handing them to EOS`, not `fanctl is leaving them alone`. Two new off-box tests cover it.
- **A sensor without an alert limit hands the fans to EOS.** A sensor that reported a reading but no usable `overheatThreshold` was left out of every check, including its own `inAlertState` and `alertCount`, with only a daily `not using …: no alert limit` notice. On a model fanctl hasn't been tested on, it could hold the fans low while that sensor was in alert. Now EOS's alarms count for every sensor with a reading, and a sensor without a usable alert limit (none, or one outside 1–150 °C, the range of a plausible reading) is a fault (`… has no usable alert limit …`) unless the operator leaves it out with `--ignore-sensor`. The reference switch reports a limit for every sensor, so nothing changes there. The unused `criticalThreshold` is no longer read. Two new off-box tests cover it.
- **The guard kills a FastCli call that times out.** `fanctl-guard.sh` cut off a FastCli call after 60 s with SIGTERM only, so a FastCli that ignored SIGTERM hung the guard for good and it never checked again. Now `timeout` sends SIGKILL, as fanctl does. The fake FastCli's wedged calls now ignore SIGTERM, so the existing off-box test covers it.
- **fanctl and the guard take turns.** The guard checked fanctl's lock, let go of it, and then restored `auto`. A fanctl that started in between (after a SIGKILL restart, for example) read the old override, then saw the guard's `auto` land, logged `fan setting changed outside fanctl` and stayed paused until restarted again. Now the guard holds fanctl's lock from deciding to restoring, and a fanctl that starts meanwhile logs `… is locked by another fanctl or by fanctl-guard; waiting` and starts as soon as the guard is done, rather than retrying every 30 s. If the runtime directory is missing (no fanctl since boot), the guard creates it as fanctl would. A new end-to-end test starts fanctl during a guard restore.
- **The guard never leaves a low override in place either.** When EOS refused `environment fan-speed auto`, the guard logged `restoring automatic fan control FAILED` every minute and left the fans at fanctl's last override, possibly 30 %, with nothing running to raise them. fanctl in the same spot tries `no environment fan-speed` and then sets `override 100`. Now the guard takes the same steps, and logs `fanctl is not managing the fans and EOS refused automatic fan control; fans set to override 100%` (err) if it comes to that. Like fanctl, it doesn't leave it there: it tries `auto` again at every check (every 60 s) while fanctl is down, logging that line each time EOS refuses, and returns the fans to automatic control within a minute of EOS accepting it. It still stops and says it failed when it can't read the setting back. Its log lines now give the setting as fanctl does (`override 40%`). New end-to-end tests pin the guard's steps and its reading of the fan setting to fanctl's.
- **`tools/report.py` reads a run cut off mid-write.** It stopped with a traceback on the normal end of a long field run, a last line the monitor never finished (`JSONDecodeError`), and on a run without an inlet reading (`min() arg is an empty sequence`). Now it skips a line that isn't a whole monitor record, warns `monitor.jsonl line N: not a monitor record, skipped` (or names the missing field), counts the skipped lines under the period, and prints `inlet       n/a (no reading)`. It lists every sensor seen in any poll, not just in the first, and counts a setting change at the last poll. New off-box tests run it on such data.
- **`tools/report.py --targets` checks its file.** A file that wasn't a saved `show system environment temperature | json`, such as a saved cooling JSON, or a sensor without a description stopped the report with a `KeyError` traceback. Now it reads the sensors the way the monitor does: a wrong, unreadable or damaged file gives one line, `--targets <file>: <what is wrong>`, before the run is read, a sensor without a description is listed by its name, and, as before and as in fanctl, a setpoint of 0 is no target. New off-box tests try five such files and a setpoint of 0.
- **`tools/monitor.py` stops on a refused login and on its own bugs.** Every error, its own included, was caught, written as an `error` record and retried at the next poll. A wrong password or a changed host key was retried every 30 s for the whole run, which can lock the account, and a bug in the alert or status code after the poll was written reset the failure count at every poll, so the `6 failures in a row` alert never came and `monitor_status.json` stopped updating without a word. Now only a failed read (a timeout, a dropped connection, a login cut short by a slow AAA server or an sshd that hangs up, a shell the switch won't open, output it can't use, such as a sensor without a name) is retried; a refused password, host key or `enable` writes `monitor stopped after N h: …` to alerts.log and exits with `monitor stopped: cannot log in: …`, and any other error writes the same alert and stops with a traceback. A bad `HOURS` prints the usage. New off-box tests cover each case.
- **`tools/monitor.py` alerts on every warning and error fanctl logs.** It and `tools/report.py` each kept their own list of the log lines that matter, and the lists had drifted: the monitor wrote nothing to alerts.log when EOS would not take the fans back (`EOS would not return to automatic fan control; fans set to override 100%`, `EOS refused automatic fan control`), the report didn't list `invalid settings, not starting`, `bad command line, not starting` or `error while judging switch environment`, and neither matched `returning to automatic fan control failed` (lower case) or most of fanctl's warnings. Now both use one case-insensitive pattern in `tools/fanlog.py`: every warning and err message from fanctl and the guard, fanctl's `taking fan control` (the end of a hand-off), ProcMgr terminations and crash loops, and EOS's `ENVMON` messages, and none of fanctl's other notice or info lines (the guard's `started` line is no longer listed). A new off-box test checks it against every message in `fanctl.py` and `fanctl-guard.sh`.
- **The step test hands the fans back to EOS however it ends.** `measurements/fan_step_test.py` finished at a static `override 40`, the reference switch's own setting, whatever the switch ran before, and on an equipment fault or overheating it set `override 70` and left it there, so a switch that normally runs EOS's automatic control was left with no reactive fan control. A missing inlet reading silently turned off its 30 °C inlet stop, it never checked that its override was still in effect (with fanctl-guard running, the guard put the fans back to automatic within a minute and the rest of each step was recorded under the wrong speed), and nothing told users to stop fanctl and the guard first (with fanctl running, fanctl stayed paused afterwards). Now it refuses to start while a `fanctl*` daemon is running (`not starting: fanctl is running. Stop it first …`), stops when the fans aren't at the speed it set or there is no inlet reading, and on a fault, too warm, Ctrl-C, an error or the normal end hands the fans back to EOS (`environment fan-speed auto`, else `no environment fan-speed`, else `override 70` with a warning; as in fanctl, a line EOS accepts without the fans going to automatic control counts as refused), then prints how it ended and the setting it found before. The range check is no longer an `assert` that `python3 -O` drops: the schedule is checked before the fans are touched. measurements/README.md says how to stop and restart both daemons. New off-box tests run the whole test against the fake switch.
- **The published SONiC benchmark numbers can be reproduced.** `bench/variants/sonic.py` took its delta from `regulate()`'s `smooth`, which fanctl 1.3 weights by fan authority, while SONiC's algorithm (and the run behind `bench/results/canonical.json` and docs/VALIDATION.md) is unweighted. Rerunning the documented command gave different numbers in 33 of 36 cases (44.75 against 27 minutes over target). It now computes the unweighted hottest 4-poll mean itself and reproduces the published results in all 36 cases. Its header now cites the upstream file it was read from at its full commit, and that project's license (GNU GPL version 3 or later), and says that no code from it is included.
- **`--status` says when fanctl is starting.** From the start until the first poll ends (several FastCli calls, longer when the switch is slow), `--status` printed `fans: None in effect; fanctl wants None`. Now it prints `fans: not read yet (fanctl is starting)`. A status file that is JSON but not a status fanctl wrote (a list, a number, no time stamp) stopped `--status` with a traceback; now it says `cannot parse …`, as for a file that isn't JSON. New off-box tests cover both.
- **A clone on Windows checks the scripts out with LF line endings.** With `core.autocrlf=true`, Git checked `fanctl.py` and `fanctl-guard.sh` out with CRLF, so `sha256sum -c SHA256SUMS` failed and a guard copied anyway would not run under bash. `.gitattributes` now keeps every text file LF on every platform.

### Upgrading from 1.3.2

- Upgrade `fanctl.py` and `fanctl-guard.sh` together, guard stopped first, as in [OPERATIONS.md](docs/OPERATIONS.md#upgrading). The guard changed: it holds fanctl's lock while it restores, falls back to `override 100` as fanctl does, and carries the version.
- Check the `exec` line first: `--flap-window`, `--reconcile`, `--summary` and `--hold-max` now have ranges, and fanctl doesn't start with a value outside one (`invalid settings, not starting: …`).
- On a model other than the reference switch, run the new `--probe` before restarting fanctl: a sensor without an alert limit, or odd PSU-fan data, now hands the fans to EOS.
- Holds and back-off carry over: 1.4.0 reads 1.3.2's memory file.

## [1.3.2] - 2026-10-26

### Changed

- **The at-target raise waits for the fans.** When a reading reached its target, fanctl raised the fans 5 % at every 15 s poll until it was under target again, faster than the temperatures can respond (time constants are minutes). On the reference switch, restarting with `--target-offset -3` put the PHY sensors exactly at their new target and took the fans from 31 % to 56 % in a minute ([details](docs/VALIDATION.md#target-offset-trial-2026-10-21)). Now the first raise is still immediate, and so is each later one while it is still getting hotter (the hottest raw excess, or the hottest smoothed weighted excess, is higher than at the last raise). Otherwise the next raise waits `up_interval` (60 s). Hand-offs to EOS are unchanged. In the controller benchmark, load-step and warm-spell overshoot, fan speed and changes per day are unchanged (all-plant mean fan 39.4 % against 39.3 %; `bench/results/v1.3.2.txt`). Two new off-box tests cover it; the suite has 100 tests.

### Upgrading from 1.3.1

Replace `fanctl.py` and restart fanctl, as in [OPERATIONS.md](docs/OPERATIONS.md#upgrading). `fanctl-guard.sh` is unchanged.

## [1.3.1] - 2026-10-21

### Fixed

- **Holds across a SIGKILL restart.** fanctl wrote its memory file when it changed the fans and when it exited on its own, but not when a hold was extended. EOS's daemon `shutdown` is a SIGKILL, so a restart during a hand-off hold resumed the hold as it was set at the hand-off, without its later extensions. fanctl now also writes the memory file at every poll while EOS has control (during a hold and while waiting for the resume conditions), so a SIGKILL restart loses at most one poll. Found in the [on-hardware hand-off test](docs/VALIDATION.md#hand-off-test-2026-10-20). A new off-box test simulates a SIGKILL restart during an extended hold.
- **Holds while paused.** When fanctl was paused (fans set outside fanctl) and handed a low manual override to EOS, later problems didn't extend the hold. Restarting fanctl to un-pause it soon after the problem cleared therefore took the fans back at once, not a full hold after the last bad reading. While paused with the fans in auto, after that hand-off or a manual `auto`, each problem now extends the hold and is written to the memory file, as when fanctl isn't paused. A new off-box test covers both cases.

### Security

- **Runtime files moved from `/tmp` to `/run/fanctl`.** The lock, status (heartbeat) and memory files keep their names. `/run/fanctl` is in RAM. fanctl creates it if it is missing, owned by root with mode 0755. It sets umask 0022 at startup, as ProcMgr does, so its files are mode 0644 even when run by hand with a stricter umask.
- **fanctl refuses to start if a runtime directory is unsafe**, for example a symlink, owned by another user, or writable by group or others. It logs `unsafe runtime directory …; not starting` and exits before it takes the lock or runs FastCli. If it can't create `/run/fanctl`, it logs `cannot create runtime directory …; not starting`.
- **`--state-file`, `--memory-file` and `--lock-file` must not contain `..`** (`bad command line, not starting`). The directory checks read a path as text, and `..` after a symlink leads to a different directory.
- **The guard trusts fanctl's lock and heartbeat only in a safe directory.** Otherwise it treats fanctl as not managing the fans and restores automatic control. It applies fanctl's ownership and permission rules with every symlink resolved. Unlike fanctl, it doesn't also check the path as written, which matters only for a non-default location reached through another user's symlink. Its warning now reads `fanctl is not managing the fans (stopped, hung, dry run or unsafe runtime directory) …`.
- **`--status` warns** with an `UNTRUSTED: unsafe runtime directory …` line and returns non-zero. It checks the directory before it opens anything in it, and doesn't hang on a FIFO planted there.

### Changed

- The guard also needs `readlink` and `dirname` (coreutils, like `stat` and `timeout`). The pre-flight `which` check lists them.
- Running fanctl by hand with the default file locations, as in the dry run, now needs root: `bash sudo /usr/bin/python3 /mnt/flash/fanctl.py --dry-run --no-syslog`. `--status` and `--probe` work without it.
- The hourly summary gives the alert limit once when the hottest sensor is also the binding sensor.
- The `--help` text for `--ignore-sensor` names sensors as `TempSensorN`, as `--probe` lists them.
- `tools/monitor.py` reads `/run/fanctl/fanctl.status.json`. `tools/report.py` only counts fanctl's hourly status lines instead of listing them as notable; `--status-lines` lists them.
- The off-box test suite has 98 tests.

### Upgrading from 1.3.0

- Re-run the pre-flight `which` check first: it now lists `readlink` and `dirname`.
- Upgrade `fanctl.py` and `fanctl-guard.sh` together, guard stopped first; [OPERATIONS.md](docs/OPERATIONS.md#upgrading) gives the order. A 1.3.0 guard can't see a 1.3.1 fanctl, and the other way round.
- The old files in `/tmp` are no longer used. They vanish at the next reload.
- Hold and back-off memory isn't carried over. Upgrade only while fanctl is in control: `--status` shows `fans: override N% in effect; fanctl wants override N%` and no `holding EOS control` line. If fanctl is waiting under EOS control, wait until it has taken over again.
- The dry-run command now needs `sudo` (above).
- `tools/monitor.py` must match the fanctl version on the switch, because each reads its own version's status file.

## [1.3.0] - 2026-10-18

The first release.

- **`fanctl.py`**: closed-loop band control of `environment fan-speed override` against EOS's own per-sensor targets, with fan-authority weighting, rate limits and probe back-off.
- **Safety layer**: hands control back to EOS automatic control on heat, faults, unreadable data or a failed write, then holds it there. If EOS refuses automatic control, it falls back to override 100.
- **`fanctl-guard.sh`**: an independent watchdog daemon that restores automatic control if fanctl stops, crashes or hangs.
- **Operator support**: `--status`, `--probe` and `--dry-run`, syslog logging, and respect for manual fan settings.
- **Evidence**: an off-box test suite (83 tests), step-test data from a real switch, a fitted plant model, and a controller benchmark. See [docs/VALIDATION.md](docs/VALIDATION.md).

## Pre-release history

Versions 1.0.0 to 1.2.0 (2026-10-16) were internal development versions. They were tested off-box only, and reviewed and hardened before release.

1.2.0 added:

- a heartbeat written at start-up
- signal-safe clean-up
- tolerance of malformed restart memory
- same-poll confirmation of operator changes
- timeouts on write verification
- a lock re-check

1.3.0 changed the following against 1.2.0:

- **Fan-authority weighting** and `--min-authority`. Each sensor's distance to its target is scaled by how strongly the fans move it. In warm rooms this runs the fans 2–16 percentage points slower on the reference switch's model.
- **Probe back-off**, persisted across restarts.
- **The binding sensor** is reported in `--status`, `--probe` and the log.
- **The interpreter** is now `/usr/bin/python3`, with the shebang `#!/usr/bin/env python3`. On EOS 4.28, `arista-python` can be Python 2.7.
- **`Controller.regulate()`** separates the in-band decision from the safety layer.
